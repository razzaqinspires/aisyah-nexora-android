# Phase 2 — Google Authentication & User Identity

## Implemented source

- Flutter Firebase initialization through generated `firebase_options.dart`.
- Google sign-in using `google_sign_in` and Firebase Authentication.
- Auth gate reacts to Firebase `authStateChanges()`.
- Fresh Firebase ID token is requested for every backend call.
- Sign-out clears Firebase and Google sessions.
- Backend verifies Firebase ID tokens with revocation checking.
- Backend provisions one internal PostgreSQL account per Firebase UID.
- `/v1/me` returns the authenticated internal account profile.
- Chat uses the backend-generated internal UUID as the owner key.
- Transaction helper uses `SET LOCAL` via `set_config(..., true)` to scope RLS identity
  to one transaction and avoid connection-pool identity leakage.

## Firebase console setup

1. Create or select a Firebase project.
2. Add an Android app using the exact Android application ID from the generated
   Flutter Android project.
3. Download `google-services.json` into `apps/android/android/app/` if using the
   native Google Services plugin.
4. Enable Authentication → Sign-in method → Google.
5. Add the debug SHA-1 and SHA-256 fingerprints. Add release fingerprints later.
6. Install FlutterFire CLI:
   `dart pub global activate flutterfire_cli`
7. From `apps/android` run:
   `flutterfire configure --platforms=android`
8. This generates `lib/firebase_options.dart`. It is project-specific and must match
   the Firebase project configured for the Android application.
9. Run `flutter pub get` and `flutter run`.

## Backend setup

1. Create PostgreSQL database and enable pgvector.
2. Apply `database/schema.sql` to a new database, or apply migration
   `database/migrations/002_identity_and_rls.sql` to an existing Phase 1 database.
3. Create a dedicated runtime DB role. It must not own application tables, be a
   superuser, or have `BYPASSRLS`.
4. Set `DATABASE_URL` in the backend environment.
5. Configure Firebase Admin Application Default Credentials or
   `GOOGLE_APPLICATION_CREDENTIALS` on the server only.
6. Run `npm install`, `npm test`, `npm run check`, then `npm run dev`.

## API

### GET /v1/me

Requires `Authorization: Bearer <Firebase ID token>`.

Returns:
- `user.id`: internal UUID generated by Nexora database
- `user.firebaseUid`: verified Firebase UID
- profile fields sourced from verified Firebase claims and upserted server-side

### POST /v1/chat

Requires the same bearer token. The backend obtains `userId` from the provisioned
account. A client-supplied `userId` is ignored.

## Data isolation design

- Firebase UID is the external authentication subject.
- `app_users.id` is the internal primary key used by application tables.
- Each protected DB transaction must call `withUserTransaction(pool, userId, callback)`.
- That helper begins a transaction, applies `app.current_user_id` with transaction-local
  scope, runs the callback, and commits/rolls back.
- Never use session-level `SET app.current_user_id` with pooled connections.
- Never trust `user_id` from request JSON, query parameters, or headers.
- Test isolation with two distinct internal UUIDs against a real PostgreSQL database
  before production deployment.

## Important limitation

The source scaffold is not a deployed Firebase project. No Firebase project ID,
OAuth client, SHA fingerprints, service-account credentials, database, or production
endpoint are supplied. These must be configured by the project owner.

## Database runtime role

See `database/ROLE_SETUP.md`. The application role must not own protected tables
and must not have `SUPERUSER` or `BYPASSRLS`. Keep migration credentials separate
from runtime credentials. RLS context is defense in depth, not a replacement for
parameterized SQL or backend hardening.
